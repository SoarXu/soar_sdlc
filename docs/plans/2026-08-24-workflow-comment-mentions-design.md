# 工作流评论与 @ 提及设计

## 背景

需求、任务和缺陷工作流中的 `add_information` 命令当前显示为“补充信息”。该动作实际调用评论接口写入 `work_item_comments`，但弹窗没有复用评论面板的提及选择逻辑，并固定提交空的 `mentioned_user_ids`。因此功能名称与数据语义不一致，且用户无法通过该入口触发 `@` 提及通知。

## 目标

- 工作流动作名称统一显示为“评论”。
- 在列表、详情和工作台中的工作流评论弹窗，支持输入 `@` 筛选项目成员、点击候选插入名称，并支持手工多选提及。
- 提交时把提及用户 ID 传给现有评论接口，复用既有权限校验、关注关系和站内通知。
- 不改变状态、处理人、流转 ID、动作键或历史评论数据。

## 方案

将评论编辑器中已经验证的提及逻辑抽为一个可复用的 `WorkItemCommentComposer` 组件。详情页评论面板使用该组件作为编辑器；工作流动作弹窗在 `command_type=add_information` 时也使用该组件。

组件接收工作项上下文、提交状态和初始内容，向父组件提交 `{ body, mentionedUserIds }`。组件通过评论候选接口加载当前工作项项目的有效成员，输入 `@` 后根据姓名/用户名显示至多 6 个候选；选中候选后将 `@显示名` 插入光标位置并同步提及 ID；多选框仍可补充或删除提及对象。这样不会出现前端可选、后端因非项目成员而拒绝保存的人员。

工作流弹窗提交时继续调用 `createWorkItemComment()`，但传入组件给出的 `mentionedUserIds`，并以“评论成功”反馈。该路径不调用工作流流转执行接口，状态保持不变。

## 范围

- 当前生效方案及默认模板中所有动作键为 `add_information` 的需求、任务、缺陷流转，显示名改为“评论”。
- 系统默认模板、后续新建方案和当前已保存的工作流定义均更新显示名。
- 详情页既有评论面板改为共享组件，行为保持一致。

不在本次范围：项目、测试用例或测试单的评论入口；评论的编辑/删除；富文本评论；改写已有评论正文或历史流转记录。

## 数据与兼容性

动作键保留 `add_information`，因为前端运行时命令与既有定义以它识别评论操作。只改 `action_name`，迁移精确处理 `action_key=add_information` 且对象类型为 `requirement`、`task`、`bug` 的定义，不改用户自定义的其他动作；若同一来源状态已有启用的“评论”动作，迁移跳过该旧动作，避免使自定义工作流产生重复按钮并无法保存。

已有 `work_item_comments`、`mentions_metadata`、提及通知与关注关系无需迁移。新组件仅把之前遗漏的 `mentioned_user_ids` 正确传至现有接口；新增只读候选接口不写入数据，并沿用评论读取的审计查看权限。

## 验证

- 默认模板：全部 `add_information` 动作名为“评论”。
- 数据迁移：仅三个工作项类型和指定动作键更新；项目及其他动作不受影响；重复执行保持稳定。
- 前端：工作流弹窗渲染共享评论编辑器；候选仅包含当前项目成员，选中 `@` 候选后提交对应用户 ID；操作名和成功提示显示“评论”。
- 后端：评论接口收到提及 ID 后写入元数据并创建通知，状态 ID 和工作流流转 ID 不变。
