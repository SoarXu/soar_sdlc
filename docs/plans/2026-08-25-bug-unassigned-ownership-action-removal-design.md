# 缺陷待分派处理人动作删除设计

## 背景

缺陷处于 `unassigned` 状态角色时尚无处理人，“指派”是设置首位处理人的唯一动作。“转派”和“变更处理人”只适用于已有处理人的阶段，与“指派”重复，不应在待处理或待分派阶段存在。

## 已确认规则

- 所有缺陷工作流一律遵循该规则，不区分系统默认、导入模板或管理员自定义图。
- 以不可编辑的 `WorkflowState.state_role = 'unassigned'` 判断待分派阶段，不依赖“待处理”或“待分派”等显示名。
- 从数据库物理删除来源状态为该角色、动作键为 `transfer` 或 `change_handler` 的流转记录。
- `waiting_iteration/待开始`、`active_work/修复中` 及其他状态中的同类动作不受影响。
- 不增加前端隐藏逻辑，也不保留虚线历史流转；已删除动作不再显示或执行。

## 方案

新增幂等 Alembic 数据迁移。迁移先关联工作流定义、状态和流转，筛选 `object_type='bug'`、`state_role='unassigned'` 与两个目标动作键，取得精确 ID 集合后执行按 ID 删除。

删除顺序为组件流转路由、流转角色引用、流转主记录。组件路由以 `RESTRICT` 外键引用流转，必须先删；角色引用虽未建外键，也随目标流转一起清理，避免孤儿数据。迁移会额外清理所有无对应流转主记录的角色引用，用于恢复曾运行早期删除逻辑但已不存在目标流转的数据库。

按 ID 选择、再删除的两阶段执行避免 MySQL 对“删除目标表同时在子查询中读取”的限制，同时在 SQLite 回归测试中可直接运行。重复升级时不会影响其他流转或工作流定义。

## 验证

- 默认、导入和自定义缺陷工作流的待分派 `transfer/change_handler` 均被删除。
- `assign`、待开始和修复中的流转仍存在。
- 非 Bug 工作流不受影响。
- 组件路由与角色引用不会引用已删除流转；迁移可重复运行。
- 降级不伪造已删除的管理员配置。
