# 问题清单逐项修复设计

## 目标

完成 `docs/issues/2026-08-18-后续问题清单.md` 中 N-001 至 N-014 的验证或修复。每个条目仅在对应自动化测试和页面行为验证通过后标记为“已解决”。

## 实施边界

- N-001 至 N-004 已有实现，重新运行其契约和接口测试，不重复改写已验证行为。
- N-005 统一任务与 Bug 列表操作容器、按钮尺寸和列宽计算。
- N-006 与需求共用可创建工作项的迭代资格约束；N-007 将工作流可执行性限制在进行中的所属迭代。
- N-008、N-009 将迭代结束时的未完成项处理改为分组、逐项选择和可追溯的延期原因。
- N-010、N-011 调整概览统计语义与工作台“当前处理人”单一责任展示、筛选。
- N-012 使角色授权可见性与当前处理人存在性解耦，并在进入必须处理的状态前校验或兜底。
- N-013 按既有评审设计及实施计划实现需求、任务、Bug 的手动/自动评审和统一评审弹窗。
- N-014 端点变更后重新生成自动连线；手工连线明确要求重置或重绘，前后端提供可理解的校验反馈。

## 方案

所有修改在一个隔离集成分支完成，但每个 N 编号具备独立测试与独立提交。后端是业务约束的最终裁决；前端只做等价预校验和清晰反馈。迁移必须可重复执行，既有数据兼容读取。评审和工作流的权限计算保持服务端单一事实来源。

## 验证策略

每个缺陷先新增最小失败测试，再实施最小修复并运行定向测试；前端使用已有 Node 契约测试风格。完成后运行后端完整测试集、前端全部契约测试和生产构建；使用既有 8 个测试账号，不创建任何用户。最后复查清单中每个条目的状态、证据和 UTF-8 编码。
