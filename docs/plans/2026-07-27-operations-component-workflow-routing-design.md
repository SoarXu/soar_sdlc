# 项目收尾与运维组件工作流路由设计

## 1. 已确认决策

- 已关闭研发项目是不可变的交付档案，不移动为运维项目子项目，也不接收新的运维事项。
- `InnovateX平台运维项目` 统一承接后续需求、任务、Bug 和运维迭代。
- 每个已结束系统可在运维项目内登记为一个业务组件；组件关联来源项目，但拥有独立的运维成员和工作流路由。
- 运维事项必须选择唯一主组件；关联组件仅表达影响范围，不参与状态图、处理人或审批链决策。
- 组件复用现有工作流引擎。项目提供默认工作流方案，组件可选择项目授权的工作流方案并配置成员路由。
- 同一工作流定义的路由与成员调整实时影响未完成事项；切换到不同工作流定义时，未完成事项保留旧定义或经过显式状态映射迁移。

## 2. 架构边界

```text
已关闭来源项目
  -> 只读来源关联

InnovateX平台运维项目
  -> 项目默认工作流方案
  -> 统一运维迭代
  -> 项目成员访问边界
  -> 业务组件
       -> 独立组件成员
       -> 可选组件工作流方案
       -> 流转处理人路由
       -> 运维事项的主组件
```

项目成员表示用户是否可以进入和操作运维项目。组件成员表示用户是否有权处理该组件作为主组件的事项；项目成员身份不自动转换为组件处理权限。

## 3. 组件创建向导

在运维项目的“业务组件”页面提供“从已关闭项目创建组件”入口：

1. 选择已关闭的来源项目，例如“QA档案管理项目”。
2. 系统预填组件名称、描述、来源项目 ID 和来源项目名称快照。
3. 系统读取来源项目成员，按预设映射生成组件成员候选项；管理员可调整角色、取消成员或确认将缺失用户加入运维项目。
4. 系统读取来源项目绑定的工作流方案，克隆为该组件可独立编辑的方案；若来源项目没有适用方案，使用运维项目默认方案。
5. 管理员确认组件负责人、成员、工作流方案和初始路由规则后创建组件。

成员和工作流均为一次性初始化副本。之后组件的任何修改不回写来源项目，也不与来源项目同步。

## 4. 工作流解析与路由

### 4.1 创建时解析

```text
创建运维事项
  -> 校验所属项目为 InnovateX平台运维项目
  -> 校验主组件启用且属于该项目
  -> 解析工作流：主组件方案 > 项目默认方案 > 系统默认方案
  -> 按事项类型取得工作流定义及初始状态
  -> 保存 workflow_definition_id、current_state_id、主组件关联
  -> 按组件路由计算默认处理人
```

一个事项的工作流定义只由主组件决定。关联组件只接收通知并参与筛选和统计。

### 4.2 流转时解析

```text
用户执行流转
  -> 根据事项的 workflow_definition_id 与 current_state_id 查找动作
  -> 校验用户具备项目访问权限
  -> 校验用户是主组件中对此动作授权的有效成员
  -> 按当前组件路由规则解析下一处理人
  -> 写入状态、处理人和审计记录
```

动作的成员范围支持指定成员、组件角色、手工选择合格成员、组件负责人和待分派池。手工选择的候选人只能是当前主组件的有效成员。

## 5. 工作流配置变化

### 5.1 同一工作流定义内修改

组件成员、成员角色、动作授权、默认处理人、动作条件和同一工作流定义中的流转配置均实时生效。未完成事项在下一次请求可执行动作或执行流转时读取最新规则。

系统必须保护在途事项：不得删除正被未完成事项作为当前状态引用的状态；不得删除使当前状态没有出路的最后一条可用流转。

### 5.2 切换不同工作流定义

组件绑定从工作流 A 改为工作流 B 时，状态 ID 没有跨定义通用性，因此不允许隐式切换在途事项。

```text
新建事项：使用工作流 B
已在途事项：继续使用工作流 A
需要切换的在途事项：执行显式工作流迁移
```

工作流迁移必须逐项或批量提供“旧定义当前状态 -> 新定义目标状态”的有效映射，并在同一事务内更新工作流定义 ID 与当前状态 ID。迁移记录必须包含前后定义、前后状态、原因和操作人。

## 6. 数据模型

| 对象 | 关键字段 |
| --- | --- |
| `business_components` | `project_id`、`source_project_id`、来源名称快照、负责人、启用状态、`workflow_scheme_id`。 |
| `component_members` | `component_id`、`user_id`、组件角色、生效状态与时间。 |
| `component_transition_routes` | `component_id`、事项类型、`transition_id`、允许成员范围、下一处理人规则、兜底策略。 |
| `work_item_components` | 事项类型、事项 ID、组件 ID、`relation_type`（`primary`/`related`）、名称快照。 |
| `workflow_migration_logs` | 事项、旧/新工作流定义、旧/新状态、原因、操作人、时间。 |

现有工作项继续保存 `workflow_definition_id` 和 `current_state_id`，不新增第二套状态引擎。

## 7. 页面与权限

- 项目详情新增“业务组件”页签；所有项目均可使用，已关闭项目只读。
- 组件详情包括基础信息、来源项目、成员、工作流、动作路由、关联事项和审计历史。
- 运维项目负责人或组件管理权限持有人可创建组件；组件负责人只能维护本人组件。
- 只有主组件对当前动作授权的有效成员可执行组件受控流转。
- 工作流迁移仅向组件负责人、运维项目负责人和系统管理员开放，且必须填写原因。

## 8. 验证要点

- 从关闭的 QA 档案管理项目创建组件后，来源成员和工作流被复制为可编辑副本，源项目数据不变。
- QA 与 ERP 组件可拥有不同成员、不同工作流和相同动作的不同处理人规则。
- QA 事项仅能由 QA 主组件授权成员流转，且可进入 InnovateX 的统一运维迭代。
- 同一定义的成员或动作规则修改后，QA 在途事项下一次流转采用新规则。
- 组件切换至不同定义后，新 QA 事项使用新定义；在途事项继续使用旧定义，除非执行有有效状态映射的迁移。
- 无效状态映射、失效组件成员、跨项目组件和删除在用状态均被后端拒绝。
