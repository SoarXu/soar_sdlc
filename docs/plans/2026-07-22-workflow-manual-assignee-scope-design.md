# 工作流手工处理人候选范围设计

## 背景

工作流配置中的“允许执行角色”限制谁能执行动作，但单条动作弹窗的“下一处理人”目前直接展示全局有效用户。后端提交时又要求下一处理人属于项目，导致界面候选范围与后端校验不一致。

## 设计

工作流动作响应新增通用的 `eligible_assignee_ids` 字段。只要动作允许手工指定处理人，后端就根据工作项所属项目查询有效项目成员；如果动作配置了 `manual_owner_roles`，继续按项目角色过滤。

`WorkflowActionButtons` 使用当前动作的 `eligible_assignee_ids` 过滤已有用户列表。指派、转派、变更处理人、转移确认和指派验证人等动作统一使用该字段。批量指派继续复用同一候选人计算函数，避免两套规则漂移。

## 边界

- “允许执行角色”仍只控制动作执行权限，不作为下一处理人的角色来源。
- 下一处理人必须是当前项目的有效成员。
- 配置 `manual_owner_roles` 时，候选人还必须具备对应项目角色。
- 候选人为空时显示空状态，不回退到全局用户。
- 后端提交校验继续作为最终保护。

## 验证

- 后端测试验证动作响应只返回当前项目有效成员，并遵守项目角色限制。
- 前端测试验证下一处理人下拉使用动作候选 ID 过滤全局用户。
- 运行完整后端工作流测试、完整前端测试和生产构建。
