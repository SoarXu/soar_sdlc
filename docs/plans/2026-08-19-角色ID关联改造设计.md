# 角色 ID 关联改造设计

## 目标

业务角色只以 `roles.id` 作为关联目标。角色名称是唯一的展示名称，修改后项目成员、工作流和分派规则均读取同一名称。系统管理员由 `users.is_system_admin` 表示，不再作为角色字典项目。

## 数据边界

- 删除 `user_roles` 和角色表中的系统管理员记录；新增 `users.is_system_admin` 并从现有系统管理员关联回填。
- `project_members` 将 `project_role` 文本迁移为 `role_id` 外键。
- 工作流的允许角色、主要处理人角色和回退角色使用关联表保存 `role_id`，不再将业务角色写入 CSV 或 JSON 字符串。
- 分派方案中角色条件改为角色 ID 关联表或 JSON 整数数组；默认模板在创建时解析并保存角色 ID。
- `creator`、`reporter`、`current_handler`、`project_member` 等保留为内置身份，不出现在角色字典，也不占用角色 ID。

## 迁移原则

迁移先按现有 `roles.role_key` 把每个旧业务角色引用解析为 ID，再写入新结构。无法解析的旧值记录为迁移失败并阻止删除旧字段，避免丢失权限配置。全部引用校验完成后才移除 `role_key`、`project_role` 及旧角色文本配置。

## 页面与接口

角色 API 只返回 `id`、名称、描述和启用状态。项目成员、工作流设计器、处理人规则和分派方案的下拉框值均为角色 ID，标签取当前角色名称。角色名称的编辑操作不需要级联更新引用数据。

## 验证

覆盖用户系统管理员布尔字段、角色改名后的项目成员与工作流展示、工作流运行时按角色 ID 授权/分派、迁移完整性和内置身份兼容性。
