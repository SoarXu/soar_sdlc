### N-001 状态删除入口与流转启停规则不一致

- 状态：已解决
- 类型：功能与数据一致性问题
- 优先级：P1
- 发现时间：2026-08-22
- 影响范围：后台管理的工作流方案详情、状态配置抽屉、流程图流转展示，以及工作流图保存接口。
- 复现步骤与证据：进入任一工作流方案详情并选择已关联流转的状态，点击“删除状态”。界面提示“请先处理与该状态关联的流转”，但既有流转只能停用、不能物理删除，因此状态删除入口无法完成操作。直接关闭状态的“启用”开关时，关联流转不会随状态自动停用或恢复，可能保留指向不可用状态的启用流转。
- 预期结果：状态配置不再提供“删除状态”按钮，以启用开关统一管理状态可用性。状态停用时，所有关联且原本启用的流转自动停用，但继续以灰色虚线保留在流程图中；状态恢复且流转两端均启用时，仅恢复此前因状态停用而自动停用的流转，原本手工停用的流转保持停用。后端保存接口执行同一一致性校正，禁止保存启用流转指向停用状态。
- 实际结果：删除入口对存在既有流转的状态不可用；状态与关联流转的启停相互独立，且停用原因没有持久化，无法安全自动恢复。
- 根因分析：状态删除入口与后端“既有流转只能停用”的历史保护规则冲突；数据模型仅保存流转启用状态，没有区分手工停用与状态联动停用，也没有在图保存边界统一校正状态和流转可用性。
- 设计说明：`docs/plans/2026-08-22-workflow-state-transition-linkage-design.md`
- 执行计划：`docs/plans/2026-08-22-workflow-state-transition-linkage-implementation.md`
- 验证结果：已解决。2026-08-22 执行 `pytest tests/test_workflow_transition_state_disable_reason_migration.py tests/test_workflow_definition_api.py -q`，48 项通过；`alembic heads` 输出唯一 head `20260822_001`，并完成后端编译检查。前端 `workflowStateAvailability`、工作流抽屉集成、自动布局和画布投影四项聚焦测试均通过，`npm test` 与 `npm run build` 均成功；`git diff --check` 通过。工作流运行时与默认模板两份历史测试仍在收集阶段引用已在 2026-08-19 角色迁移中移除的 `UserRole` 模型，已确认为无关的既有测试债务，未作为本问题的回归失败。
- 回归补充（2026-08-24）：实际停用状态后，关联流转在画布中消失，违反上述“灰色虚线保留”要求。根因是前端画布投影按状态启用值过滤边，导致既有禁用边样式无法接收该流转；流转记录及其 `enabled=false`、`auto_disabled_by_state` 数据仍被正确保留。本轮仅修正投影与回归测试，状态联动和后端保存规则不变。

### N-002 工作项状态未按处理人和迭代阶段匹配

- 状态：已解决
- 类型：功能与数据一致性问题
- 优先级：P1
- 发现时间：2026-08-22
- 影响范围：需求、任务和 Bug 的创建、认领、指派、取消指派、迭代启动、迭代移动、工作流状态及操作按钮。
- 复现步骤与证据：在未开始或进行中的迭代内创建需求、任务或 Bug，并分别选择或不选择当前处理人。当前实现无论是否选择处理人都进入工作流初始状态；默认需求和任务初始状态为“待分派”，因此会出现已有处理人但仍显示待分派。迭代启动又明确不改变子工作项状态，无法在迭代开始时把已分派事项转入处理中或修复中。
- 预期结果：未开始迭代中，无处理人的事项为“待分派”，有处理人的事项为“待开始”；进行中迭代中，无处理人的事项为“待分派”，有处理人的需求和任务为“处理中”、Bug 为“修复中”。未开始迭代内后续认领或指派进入“待开始”；迭代启动时自动通过正式流转将“待开始”事项转入执行状态并记录历史。取消指派返回“待分派”；待开始事项移入进行中迭代时自动启动，执行中事项不得直接移回未开始迭代。
- 实际结果：工作项状态只取工作流定义的统一初始状态，处理人和迭代阶段不会驱动创建后状态或迭代启动联动；已有处理人、迭代未开始和实际执行状态之间缺少“待开始”语义。
- 根因分析：现有工作流状态只有可编辑名称、分类和不可变 ID，没有稳定标识“待分派、待开始、执行中”系统语义的角色；创建服务统一写入 `initial_state_id`，认领/指派目标固定，迭代启动服务只更新迭代自身及项目层级，不执行子工作项正式流转。

- 执行计划：`docs/plans/2026-08-22-work-item-state-matrix-implementation.md`
- 验证计划：`docs/plans/2026-08-22-work-item-state-matrix-validation.md`

### N-005 任务不支持子任务及需求任务层级一致性约束

- 状态：已解决
- 类型：功能与数据一致性问题
- 优先级：P1
- 发现时间：2026-08-22
- 影响范围：任务数据模型、任务创建与编辑接口、任务列表及详情页、项目详情“任务”页签、任务工作流完成/取消校验和阻断提示。
- 复现步骤与证据：当前任务创建界面只能关联项目和需求，无法指定父任务，也无法从某个任务下直接创建子任务。`Task` 模型、`TaskCreate/TaskUpdate/TaskRead` 接口均没有父任务字段；默认任务工作流的完成和取消流转也没有校验关联子任务状态。
- 预期结果：任务支持创建任意层级的子任务，并能在父任务详情中查看和继续创建下级任务。一棵任务树共享同一项目、需求和迭代；子任务创建时继承父任务归属且不能单独脱离，根任务或关联需求移动时原子同步整棵任务树，并按 N-002 状态矩阵更新各任务状态。父任务进入“已完成”或“已取消”终态前，必须递归检查所有直接及间接子任务；只有全部子任务均已完成或已取消时才允许流转。存在未结束子任务时阻断父任务操作并返回未结束子任务清单，由用户逐项处理，不自动完成或取消子任务。
- 实际结果：任务之间没有父子层级关系，无法创建、查询或展示子任务；父任务完成或取消时也没有关联子任务状态的校验机制。
- 根因分析：任务表缺少自关联父任务外键及层级关系，任务接口和前端表单没有传递父任务上下文；工作流运行时已有需求、Bug、迭代和项目终态校验器，但没有面向任务层级的终态校验器，任务默认模板的终态流转也未配置相应校验规则。
- 已确认规则：完成与取消采用统一阻断策略；校验覆盖所有层级后代；允许通过的子任务终态为“已完成”或“已取消”；阻断时展示未结束子任务，不执行级联状态修改。一棵任务树只能关联同一个需求，并始终与该需求保持同项目、同迭代；根任务调整归属时同步整棵树，子任务不得单独调整项目、需求或迭代；任一节点不满足移动条件时整体回滚并返回阻断清单。
- 前置依赖：先完成 N-002 的稳定状态角色、状态矩阵和迭代移动状态联动；N-005 复用其正式流转与审计能力，不自行直接改写工作流状态。
- 设计说明：`docs/plans/2026-08-22-task-hierarchy-consistency-design.md`
- 执行计划：`docs/plans/2026-08-22-task-hierarchy-consistency-implementation.md`
- 验证计划：`docs/plans/2026-08-22-task-hierarchy-consistency-validation.md`
- 验证结果：已解决。2026-08-24 以 `bob` 打开三层任务树根任务：详情页展示两个直接子任务、父子链接和“新增子任务”。从该入口创建浏览器验收子任务，项目、需求和迭代均为只读继承字段，创建后子任务列显示为待分派且归属待规划迭代。尝试取消根任务时，页面弹出“存在未结束子任务，无法结束任务”，精确列出两个直接子任务和一个孙任务共 3 项，根任务及后代状态均未改变。此前已完成迁移、服务、接口、任务树移动和终态阻断自动化回归；完整后端 `pytest -q` 的历史 `UserRole` 导入债务不属于本项。

### N-007 工作台全量聚合导致大数据量加载缓慢

- 状态：已解决
- 类型：性能问题
- 优先级：P1
- 发现时间：2026-08-22
- 影响范围：工作台进行中迭代工作项接口、筛选与分页、工作流动作批量加载、前端首次加载及筛选响应时间。
- 复现步骤与证据：当前用户可见的进行中迭代累计上百条需求、任务和 Bug 时打开工作台。现有 `/dashboard/workbench` 会同时计算进行中工作项、待处理、未分派、终态、我发起、我关注、提及、异常、代码评审等完整集合；多处先执行 `.all()` 再在 Python 中按项目、迭代和状态过滤，任务迭代还存在逐条回查。前端收到全部进行中工作项后才执行筛选、排序和分页，并为全部工作项批量加载工作流动作，而表格实际只展示当前 20 条。
- 预期结果：工作台进行中迭代列表采用服务端筛选、稳定排序和分页，数据库只返回当前页工作项及总数；前端只为当前页加载工作流动作。筛选选项仍覆盖当前用户完整可见范围，分页、权限、终态展示和批量操作行为不变；旧聚合接口保留兼容，避免影响仍消费其他工作台分区的调用方。
- 实际结果：数据库扫描和构造多个页面未使用的完整集合，响应体包含全部工作项，前端重复完成过滤、排序和切片，工作流动作请求规模也随总数据量增长，导致首屏等待时间随数据量近似线性增加。
