# 工作项删除一致性设计

## 目标

已完成任务与其他可删除任务采用同一删除入口规则；需求存在未删除关联任务时，拒绝删除需求并完整保留关联关系与审计记录。

## 方案

任务列表、项目任务列表和任务详情页统一以 `canDeleteWorkItem` 与项目/迭代可变性为准，不再以工作流终态隐藏删除入口。删除 API 仍由服务端授权校验，前端仅负责正确呈现入口。

删除需求时，服务层先在同一事务中统计 `requirement_id` 指向该需求且 `deleted = 0` 的任务。数量大于零即返回 `409 REQUIREMENT_HAS_LINKED_TASKS`，响应包含 `linked_task_count` 与中文提示。检查必须发生在更新任务、测试用例、需求或审计日志之前，因此失败没有部分写入。没有关联任务时继续沿用既有的测试用例解绑及软删除逻辑。

## 错误与兼容

需求删除冲突使用稳定错误码，不依赖错误文案解析。前端通过现有 `showActionError` 展示后端中文消息。已删除任务不参与阻断；N-005 任务树共享需求，因此根、子、孙任务均计入同一次检查。

## 验证

后端 API 覆盖已完成任务删除、树中任一活动任务阻断需求删除、已删除任务不阻断、失败后关联和审计不变。前端源契约覆盖三处任务入口的删除可见性及需求删除错误反馈，最后运行相关回归、全量前端测试和生产构建。
