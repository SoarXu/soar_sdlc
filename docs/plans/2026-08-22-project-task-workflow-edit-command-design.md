# 项目详情任务编辑命令统一设计

## 背景

项目详情“任务”页签存在两套编辑入口：页面模板硬编码的“编辑”按钮，以及 `WorkflowActionButtons` 根据当前工作流返回的 `command_type=edit` 动作。前者直接调用 `openTaskEdit(row)`，后者只向父页面发出 `command` 事件。

当前任务列表没有监听该事件，所以工作流配置为“更多操作”的编辑动作虽然可以显示，却无法打开编辑弹窗。硬编码按钮又始终按页面权限显示，导致同一行出现两个编辑入口，并使工作流中的主操作/更多操作配置失去控制力。

需求列表已经采用正确模式：不固定渲染编辑按钮，由工作流决定可见性和分组，父页面监听命令并复用既有编辑弹窗。

## 目标

- 项目详情任务编辑入口只由工作流动作决定是否显示及显示位置。
- 工作流编辑动作无论位于主操作还是更多操作，都能打开现有任务编辑弹窗。
- 保持任务编辑表单、保存接口和刷新逻辑不变。
- 保留删除等页面固有操作，不把它们迁入工作流。
- 增加任务级回归测试，防止再次只覆盖需求。

## 非目标

- 不修改后端工作流定义、动作权限或运行时接口。
- 不把 `edit` 命令当作状态流转提交到后端。
- 不改变任务编辑字段、保存校验或处理人规则。
- 不在本问题中移除 Bug 固定编辑入口；默认 Bug 工作流当前没有编辑命令，直接移除会造成能力缺失。

## 方案比较

### 方案一：保留固定按钮并隐藏工作流编辑动作

可以消除重复，但“编辑”将不再服从工作流的主操作、更多操作和权限配置，与已经确定的配置职责相冲突。

### 方案二：在动作组件内部直接打开任务编辑弹窗

动作组件无法持有项目详情的任务表单、选项数据和保存上下文。把业务页面弹窗逻辑下沉到通用组件会增加耦合，并破坏需求、任务、Bug 共用组件的边界。

### 方案三：移除固定入口并由父页面处理工作流命令

任务列表只渲染 `WorkflowActionButtons`，父页面监听其 `command` 事件，将 `edit` 转发到现有 `openTaskEdit(row)`。该模式与需求列表及全局任务列表一致，改动范围最小。

采用方案三。

## 组件职责

### `WorkflowActionButtons`

- 根据运行时动作的 `ui_config.list_display` 决定主操作或更多操作。
- 对 `command_type=edit` 只发出 `{ commandType, action }`，不提交状态流转，也不直接操作业务弹窗。
- 保持现有行为，不需要修改。

### `ProjectDetailView`

- 删除任务操作列中直接调用 `openTaskEdit(row)` 的固定按钮。
- 为任务的 `WorkflowActionButtons` 增加 `@command="handleTaskWorkflowCommand(row, $event)"`。
- 新增任务命令处理函数；仅在 `commandType === 'edit'` 时调用现有 `openTaskEdit(row)`。
- 保留 `@executed="refreshAfterMutation"`，用于真正执行工作流流转后的列表刷新。
- 保留删除按钮及其页面权限判断。

## 权限与数据流

编辑动作的可见性由后端工作流运行时根据当前状态、允许角色和项目权限返回。前端不再使用 `canEditWorkItem(row)` 额外生成第二条编辑入口。

点击路径为：

1. 用户点击主操作中的“编辑”，或“更多”菜单中的“编辑”。
2. `WorkflowActionButtons.openAction()` 识别 `command_type=edit`。
3. 组件发出 `command` 事件，不调用工作流执行 API。
4. `ProjectDetailView.handleTaskWorkflowCommand()` 调用 `openTaskEdit(row)`。
5. 现有任务编辑弹窗加载当前行数据；保存仍调用原任务更新接口。

工作流未返回编辑动作时，任务行不显示编辑入口。这样显示位置、可见状态和允许角色均与方案配置一致。

## Bug 入口审计

项目详情 Bug 页签同样存在固定编辑按钮，且当前未监听工作流命令。但默认 Bug 工作流没有 `edit` 命令，因此它目前不是重复入口。验证阶段需要记录这一差异，确保本次任务修复没有误删 Bug 编辑能力；后续若将 Bug 编辑纳入工作流，应单独补齐默认动作、命令处理和迁移后再移除固定入口。

## 测试设计

扩展 `projectDetailWorkflowIterationLayout.test.mjs`：

- 截取任务页签模板，断言不再存在固定 `openTaskEdit(row)` 编辑按钮。
- 断言任务页签保留 `WorkflowActionButtons`。
- 断言任务动作组件监听 `@command="handleTaskWorkflowCommand(row, $event)"`。
- 断言任务命令处理函数将 `edit` 转发给 `openTaskEdit(row)`。
- 断言任务删除操作仍保留。
- 保留既有需求断言，证明两类对象遵循相同模式。
- 对 Bug 页签增加审计断言，明确当前固定编辑入口仍保留且默认模板没有工作流编辑动作，防止无意删除。

聚焦测试通过后运行前端全量测试和生产构建。页面验收分别覆盖编辑动作配置为主操作、更多操作，以及当前状态不返回编辑动作三种情况。
