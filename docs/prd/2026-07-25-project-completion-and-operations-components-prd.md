# 项目收尾与运维组件承接 PRD（草案）

## 1. 背景

研发项目完成交付后，原项目需要保留完整、不可被后续运维工作改写的交付历史；但上线系统仍会产生缺陷、配置调整、小改造和版本升级等运维需求。将已结束研发项目移动为运维项目的子项目，会混淆项目的交付边界、成员边界和工作项归属，不能作为运维承接方式。

本 PRD 定义以长期运维项目承接后续工作、以业务组件关联原项目并按组件路由成员和工作流的规则。

## 2. 目标与非目标

### 2.1 目标

- 研发项目结束后保持历史和成员名单不变。
- 运维需求、任务和 Bug 创建在长期运维项目下，可追溯至一个已结束研发项目。
- 每个原项目在运维项目中可登记为一个业务组件，并维护独立的运维成员名单。
- 基于主组件决定新运维事项的默认工作流方案、默认处理人和流转参与人。
- 支持一条运维事项影响多个已结束项目，同时保持唯一责任归属。

### 2.2 非目标

- 不将已结束研发项目移动为运维项目的子项目。
- 不修改原项目、原项目成员、原工作项、原迭代和原工作流历史。
- 不以“工作流设计器组件注册表”承载业务组件；两者是不同概念。
- 第一阶段不建设服务台门户、SLA、值班排班、外部客户协同或 CMDB。

## 3. 核心概念

| 概念 | 定义 | 关系 |
| --- | --- | --- |
| 原项目 | 已完成并关闭的研发项目，是交付历史档案。 | 可作为一个或多个运维组件的来源。 |
| 运维项目 | 长期存续的项目，承接上线后的新需求、任务、Bug 和运维迭代。 | 拥有业务组件和运维成员。 |
| 业务组件 | 运维项目内的责任与影响范围单元，例如“商城一期”“支付服务”。 | 可关联一个原项目、独立成员和路由规则。 |
| 主组件 | 运维事项唯一必选的业务组件。 | 决定责任团队、默认路由和默认工作流方案。 |
| 关联组件 | 运维事项可选的多个附加组件。 | 只表达影响范围、通知和统计，不争夺流程控制权。 |
| 组件成员 | 为组件新建的运维责任名单。 | 与原项目成员独立维护。 |

## 4. 项目收尾与冻结

### 4.1 关闭前置条件

- 项目负责人或管理员发起“关闭项目”动作。
- 项目关联的迭代必须均为终态。
- 项目内需求、任务、Bug、测试单等工作项必须满足各自的终态规则；存在未完成项时，系统返回阻断清单。
- 关闭动作必须记录实际完成日期、操作人和备注。

### 4.2 关闭后的冻结规则

- 原项目不可再新增、编辑、删除或流转其工作项，也不可新增或调整迭代。
- 原项目的成员、负责人、工作流方案、项目层级和业务基础信息不可修改。
- 原项目仅可查看历史、导出和审计；不得为了处理新运维需求而重新激活。
- 原项目不得被移动到运维项目下，也不得因创建运维组件改变其项目归属。

## 5. 业务组件

### 5.1 创建与来源关联

- 组件只能在一个活跃的运维项目下创建。
- 创建组件时可选择一个已关闭原项目作为“来源项目”；同一运维项目中，同一原项目最多登记一个有效组件。
- 组件保存来源项目 ID、来源项目名称快照、组件名称、说明、启用状态和组件负责人。
- 来源项目名称后续即使发生展示调整，已有组件仍保留创建时的名称快照和关联 ID。
- 组件停用后，不可作为新运维事项的主组件；历史事项继续保留原组件关联。

### 5.2 组件成员

- 组件成员名单独立于原项目成员名单；原项目关闭后不得由组件成员变更反向修改原项目成员。
- 组件成员必须同时是运维项目的有效成员，避免绕过运维项目权限边界。
- 运维项目成员资格只表示用户可以进入该运维项目；它不自动授予任何组件的处理、评审或审批资格。组件成员名单是运维事项路由和流转授权的唯一成员依据。
- 每个组件单独维护成员名单、角色、默认处理人和流转授权。组件 A 的成员和规则不得自动继承给组件 B；同一用户可以在不同组件承担不同角色。
- 第一阶段支持以下组件角色：

| 角色 | 职责 |
| --- | --- |
| 组件负责人 | 维护组件、成员与路由规则；接收升级通知。 |
| 处理人 | 接收默认指派并执行处理类流转。 |
| 评审人 | 执行评审、验收或复核类流转。 |
| 审批人 | 执行需要审批的流转。 |

- 成员移除只影响之后创建的事项和未被明确指派的待办；已完成事项的历史处理人和当时成员身份必须保留快照。
- 组件负责人变更必须写入审计记录，不能覆盖历史事项的处理人记录。

### 5.3 独立团队示例

```text
运维项目：企业应用运维

组件：ERP 系统
  成员：张三（负责人、处理人）、李四（评审人）

组件：MES 系统
  成员：王五（负责人、处理人）、赵六（审批人）
```

ERP 运维需求只能按 ERP 组件的成员和规则流转，MES 运维需求只能按 MES 组件的成员和规则流转；两套成员名单互不影响。

## 6. 运维事项创建与项目关联

### 6.1 创建规则

```text
创建运维需求/任务/Bug
  -> 选择运维项目
  -> 选择主组件（必选）
  -> 选择关联组件（可选，多选）
  -> 选择该运维项目下的迭代（可选）
  -> 系统生成事项并执行组件路由
```

- 新事项的 `project_id` 必须是运维项目，不能是已关闭原项目。
- 新事项必须有一个启用的主组件；主组件须属于该运维项目。
- 关联组件可为零到多个，且不得与主组件重复。
- 主组件关联的来源项目是该事项的主来源项目；关联组件的来源项目形成附加影响范围。
- 一般事项只选择一个主组件。跨系统接口、共享组件、统一安全修复、链路故障和数据迁移等场景可添加关联组件。

### 6.2 运维迭代

- 运维迭代归属运维项目；仅该运维项目下的运维事项可进入该迭代。
- 原项目的历史迭代不接收运维事项，也不因运维事项发生变化。
- 紧急事项可不进入迭代；常规改造可进入运维项目的计划迭代。

## 7. 工作流与组件路由

### 7.1 统一工作流能力

继续使用系统现有的工作流定义、状态节点、流转、权限校验、处理人规则和状态历史，不新增第二套运维状态引擎。运维项目可绑定运维工作流方案，方案按事项类型定义需求、任务和 Bug 的状态图。

### 7.2 组件路由规则

- 主组件可配置默认工作流方案；未配置时继承运维项目的工作流方案。
- 组件只能选择其所属项目已启用并授权的工作流方案；创建事项时，系统按“主组件方案优先、运维项目方案兜底、系统方案最后兜底”解析工作流定义和初始状态。
- 事项保存解析后的工作流定义 ID 和状态 ID。组件对同一工作流定义的成员、角色、动作授权和下一处理人规则修改，应实时影响该组件下未完成事项的后续流转。
- 组件切换到另一工作流定义时，不能直接覆盖未完成事项的工作流定义 ID；新建事项使用新定义，未完成事项继续使用原定义，或通过显式工作流迁移完成切换。
- 主组件可为每个事项类型、每个流转动作独立配置允许的组件角色、指定用户、默认下一处理人角色和无可用成员时的兜底策略。不同组件可以采用不同的配置。
- 创建后默认处理人按规则解析：指定处理人 > 主组件处理人 > 主组件负责人 > 待分派。
- 流转权限同时满足运维项目权限和主组件角色要求；系统管理员仍保留平台级兜底权限，并写入代处理审计。
- 关联组件不得改变状态图、下一处理人或审批链；它们仅接收通知、展示影响范围并参与报表。

### 7.3 组件流转成员选择

每个组件的每个流转动作可独立选择下列成员范围之一：

| 配置方式 | 含义 |
| --- | --- |
| 指定成员 | 仅指定的一名或多名组件成员可执行，或作为下一处理人。 |
| 组件角色 | 当前组件中具有指定角色的所有有效成员可执行。 |
| 手工选择 | 操作人从当前组件满足角色要求的有效成员中选择下一处理人。 |
| 组件负责人 | 路由给当前组件负责人。 |
| 待分派 | 不自动指定人员，进入组件待分派池，由组件负责人或授权成员认领。 |

当配置的成员已失效、被移出组件或不再属于运维项目时，系统不得把事项指派给该成员；应按该动作的兜底策略进入待分派、交由组件负责人处理，或阻止动作并提示维护组件成员。

### 7.4 工作流迁移

- 仅允许组件负责人、运维项目负责人或系统管理员发起未完成事项的工作流迁移。
- 迁移前必须为旧工作流中每个被迁移事项的当前状态，选择新工作流中的一个目标状态；未提供有效映射时，系统拒绝迁移。
- 系统在一个事务中更新事项的工作流定义 ID 和当前状态 ID，并记录旧定义 ID、旧状态 ID、新定义 ID、新状态 ID、操作人、时间和迁移原因。
- 不允许通过普通组件编辑或工作流绑定操作，隐式改变未完成事项的工作流定义 ID。
- 工作流定义内的状态、流转和动作规则修改会实时影响使用该定义的未完成事项；系统必须阻止删除仍被未完成事项作为当前状态引用的状态，或删除会使该状态没有可用后续流转的最后一条流转。

### 7.5 示例

```text
运维项目：商城运维
主组件：商城一期（来源项目：商城一期研发）
关联组件：支付服务（来源项目：支付研发）

创建“订单退款失败”运维需求
  -> 采用“商城一期”配置的运维需求工作流
  -> 默认指派给“商城一期”的组件处理人
  -> 支付服务成员收到关联通知
  -> 评审/审批时仅以主组件定义的角色和规则为准
```

## 8. 权限与审计

- 运维项目负责人或具备组件管理权限的成员可创建、编辑、启停组件及维护组件成员。
- 组件负责人只能维护本人负责组件的成员和路由配置，不能修改来源项目。
- 普通运维项目成员只能在授权范围内创建事项、处理事项或查看组件信息。
- 只有主组件授权的有效成员才可执行该事项的组件受控流转；仅是运维项目成员、关联组件成员或原项目历史成员均不构成流转授权。
- 所有组件、组件成员、来源关联、工作流方案绑定、默认处理人和流转授权的变更必须记录操作人、时间、前后值和原因。
- 历史事项的主组件、关联组件、创建时工作流方案、处理人和关键成员角色需保留快照，用于审计与报表回放。

## 9. 数据与界面需求

### 9.1 数据对象

| 对象 | 必要字段 |
| --- | --- |
| 业务组件 | 运维项目 ID、来源项目 ID、来源项目名称快照、名称、说明、负责人、状态、默认工作流方案 ID、默认处理人规则。 |
| 组件成员 | 组件 ID、用户 ID、组件角色、启用状态、生效时间、失效时间。 |
| 事项-组件关联 | 事项类型、事项 ID、组件 ID、关联类型（主组件/关联组件）、组件名称快照。 |
| 组件流转规则 | 组件 ID、事项类型、流转 ID、允许角色、下一处理人角色、兜底策略。 |
| 工作流迁移记录 | 事项类型、事项 ID、旧工作流定义 ID、旧状态 ID、新工作流定义 ID、新状态 ID、迁移原因、操作人、操作时间。 |

### 9.2 界面入口

- 运维项目详情增加“业务组件”页签，展示来源项目、负责人、成员数、状态和未完成事项数。
- 组件详情展示成员、路由规则、关联事项和来源项目的只读跳转。
- 运维需求、任务、Bug 的创建与编辑表单增加“主组件”和“关联组件”字段；主组件变更须重新计算未来可执行动作和默认处理人，并记录审计。
- 原项目详情只展示“被哪些运维组件承接”的只读关联，不展示或编辑运维成员名单。
- 运维项目列表、迭代、工作台和报表支持按主组件及关联组件筛选。

## 10. 验收标准

1. 关闭原项目后，无法修改其成员、工作项、迭代、工作流方案和项目层级。
2. 在运维项目创建需求时，无法将已关闭原项目作为需求所属项目，但可选择其对应组件作为主组件。
3. 组件成员变更不会改变原项目成员或原项目历史工作项。
4. 创建事项后，系统按主组件配置解析并固化工作流与默认处理人；关联组件不改变主流程。
5. 单一项目事项可只选择一个主组件；跨项目事项可增加多个关联组件，且系统仍只有一个主责任组件。
6. 停用组件后，不能创建以该组件为主组件的新事项，历史关联仍可查询。
7. 所有组件、成员和路由配置变更均可在审计记录中查看。
8. 两个组件可配置不同的成员名单和相同流转动作的不同授权范围；事项只能由其主组件授权的有效成员流转。
9. 修改同一工作流定义的动作授权或处理人规则后，使用该定义的未完成事项在后续流转时立即采用新规则。
10. 将组件改绑到不同工作流定义时，未完成事项不会隐式切换；只有新建事项使用新定义，或由授权人员完成有效状态映射后显式迁移。

## 11. 与现有主 PRD 的关系

本 PRD 取代主 PRD 中“项目完成后可转移到运维类主项目下继续管理、后续工作仍创建在原项目”的规则。后续实现和验收以本 PRD 为准。
