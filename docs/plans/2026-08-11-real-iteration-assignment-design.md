# 真实迭代分配设计

## 目标

取消项目级“需求池”默认迭代。每个需求必须归属其项目范围内处于未开始或进行中的真实迭代；创建和修改均不得留空或使用已关闭迭代。

## 数据迁移

迁移会逐项目处理现有需求池。优先选择该项目范围内的进行中迭代，其次选择未开始迭代；若两者都不存在，则创建一个使用默认迭代工作流的未开始迭代。需求池内的需求、任务和 Bug 迁移到该目标迭代，并保留迭代历史记录。迁移完成后删除需求池记录及项目到需求池的关联，移除对应的旧模型、服务和数据库字段。

## 业务约束

需求创建、编辑、批量导入、跨项目移动和迭代关联操作统一调用同一项迭代资格校验：目标迭代存在、属于项目范围、不是关闭状态，且状态分类为未开始或进行中。缺少迭代或传入已关闭迭代时，后端返回明确的校验错误。任务和 Bug 不再回退到需求池；关联需求时继承其迭代，无关联时使用项目的可用真实迭代，必要时自动创建未开始迭代。

## 界面

需求新增和编辑表单只提供当前项目的未开始或进行中迭代，字段为必填且不可清空；项目详情中的新增需求遵循相同规则。项目详情继续展示“待规划工作池”区域，但不再把它当作迭代或筛选入口，而是汇总项目进行中与未开始迭代中的需求、任务和 Bug。原“纳入正式迭代”操作随需求池移除。

## 验证

后端 API 测试覆盖空迭代、关闭迭代、项目外迭代、无可用迭代的自动创建及存量迁移；前端源级契约测试覆盖必填选择器、可选状态过滤和工作池聚合。先验证测试因旧的需求池逻辑而失败，再实现最小变更，最后运行前后端全量测试与构建。
