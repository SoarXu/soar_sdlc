# 项目需求池迭代设计

## 1. 背景与目标

当前需求允许 `iteration_id` 为空，未排期需求仅在项目详情中查看。新的业务要求是：任何需求都不能处于没有迭代归属的状态，同时不能因为暂时没有合适的交付迭代而阻塞需求录入。

每个项目在创建时自动生成一个系统需求池迭代。用户创建需求时如果未选择正式迭代，系统将需求自动放入该项目的需求池。需求池用于表达“尚未排入正式交付迭代”，不参与正常迭代执行、工作台或交付统计。

本设计只强制需求始终具有迭代归属，不改变任务、Bug 和测试对象允许直接迭代为空的现有规则。

## 2. 核心决策

- 每个项目只有一个系统需求池迭代。
- 项目与需求池在同一事务中创建；需求池创建失败时项目创建整体回滚。
- 需求池默认名称为“需求池”，允许项目负责人或管理员修改名称。
- 业务判断不依赖需求池名称，只依赖稳定标识和项目保存的需求池引用。
- 用户创建的普通迭代始终标识为非需求池，保留现有编辑、删除和工作流能力。
- 未选择迭代、清空迭代或从正式迭代移除需求，都表示将需求放回所属项目的需求池。
- 完成存量迁移后，数据库中的需求迭代归属收紧为非空。

## 3. 数据模型

### 3.1 迭代标识

在 `iterations` 增加：

```text
is_requirement_pool TINYINT(1) NOT NULL DEFAULT 0
```

- `1`：系统需求池迭代。
- `0`：用户创建的普通交付迭代。
- 该字段只由系统写入，不出现在创建或编辑迭代的可写请求字段中。

### 3.2 项目需求池引用

在 `projects` 增加：

```text
requirement_pool_iteration_id BIGINT NULL
```

该字段通过外键关联 `iterations.id`，并增加唯一约束，表示项目唯一、规范的需求池迭代。字段在物理结构上允许为空，以支持“先插入项目取得自增 ID，再创建需求池并回写项目”的同一事务创建顺序；事务提交前服务层必须保证有效项目已设置该引用。

`iterations.is_requirement_pool` 负责定义迭代行为，`projects.requirement_pool_iteration_id` 负责唯一定位项目使用的需求池。名称修改不影响两者。

需求池仍在 `iteration_projects` 中只关联其所属项目，不允许关联其他项目或修改项目范围。

### 3.3 需求归属约束

存量数据完成回填后：

- `requirements.iteration_id` 改为 `NOT NULL`；
- 增加 `requirements.iteration_id -> iterations.id` 外键；
- 删除迭代继续采用软删除，需求池额外禁止删除，避免产生失效引用。

## 4. 创建与变更流程

### 4.1 创建项目

1. 创建项目记录并取得项目 ID。
2. 使用系统迭代工作流的初始状态创建需求池，设置 `is_requirement_pool = 1`、默认名称“需求池”，不设置起止日期。
3. 在 `iteration_projects` 中将需求池只关联当前项目。
4. 将需求池 ID 写入项目的 `requirement_pool_iteration_id`。
5. 在同一事务内提交全部数据；任一步失败都整体回滚。

需求池由于现有迭代表要求工作流定义和当前状态非空，仍保存合法的初始工作流身份，但不对外暴露任何迭代流转动作。

### 4.2 创建需求

- 明确选择正式迭代：沿用现有迭代可变性与项目范围校验。
- 未传或传入空 `iteration_id`：后端读取项目的 `requirement_pool_iteration_id` 并写入需求。
- 前端新建表单默认选中“需求池（未排期）”，后端兜底规则仍必须生效。
- 需求创建和需求池归属历史在同一事务内记录。

### 4.3 编辑、移除和换项目

- 编辑需求并将迭代清空：转换为所属项目需求池 ID，不在数据库中写入空值。
- 从迭代详情移除需求：移动到需求所属项目的需求池，并记录离开正式迭代、进入需求池的完整历史。
- 需求从需求池转入正式迭代：执行现有范围和迭代可变性校验。
- 需求更换项目且当前处于原项目需求池：自动移动到新项目需求池。
- 需求更换项目且当前处于正式迭代：正式迭代覆盖新项目时可保留，否则拒绝保存并要求选择新项目范围内的迭代。
- 需求导入未指定迭代：新增需求进入对应项目需求池；更新已有需求不无条件覆盖原迭代归属。

## 5. 需求池保护

当 `is_requirement_pool = 1` 时：

- 允许修改名称，并记录更新人和审计日志；
- 禁止删除；
- 禁止启动、暂停、恢复、完成、取消等工作流流转；
- 禁止修改负责人、日期、目标、生命周期阶段及关联项目范围；
- 禁止修改 `is_requirement_pool`；
- 禁止通过普通迭代创建接口创建需求池。

保护规则必须在服务端统一执行。前端隐藏按钮只用于改善交互，不能作为完整性边界。

若项目需求池引用缺失、引用的迭代未标识为需求池，或者需求池未只关联当前项目，服务端返回明确的数据完整性错误，不自动创建第二个需求池。正常运行时不提供补建分支。

## 6. 查询与界面

- 项目需求列表和迭代筛选显示需求池，展示名称为用户修改后的实际名称，并可补充“未排期”语义。
- 新建需求时默认选中项目需求池，允许改选正式迭代。
- 编辑需求时允许选择需求池，作为“退回待排期”的明确操作。
- 项目需求页向有管理权限的用户提供“重命名需求池”操作。
- 项目的正常迭代列表和迭代详情入口排除需求池。
- 工作台、燃尽图、迭代进度、完成率和交付统计按 `is_requirement_pool = 1` 排除需求池，不依赖工作流状态或名称。
- 需求池中的任务若通过需求继承有效迭代，也按需求池范围排除在活动迭代工作台之外。
- 读取接口返回 `is_requirement_pool`；该字段为只读。前端可据此区分选择项与正式迭代列表。

## 7. 权限与错误处理

- 项目负责人和管理员可重命名需求池；其他用户只能在其现有需求操作权限范围内选择需求池或正式迭代。
- 项目需求池创建失败时，项目创建返回失败，不留下半成品项目。
- 当请求尝试删除、流转或修改需求池受保护字段时，返回稳定的业务错误码和可读说明。
- 当项目需求池关系损坏时，拒绝创建或移动需求，并报告数据完整性错误，避免产生空归属或错误归属。
- 项目删除时沿用现有级联软删除规则处理需求及其需求池；历史引用保持可审计。

## 8. 存量迁移

迁移按以下顺序执行：

1. 为迭代增加 `is_requirement_pool`，默认将所有现有迭代标记为普通迭代。
2. 为项目增加可空的 `requirement_pool_iteration_id`、外键和唯一约束。
3. 为每个存量项目创建一个需求池，并回写项目引用；软删除项目的需求池保持对应的软删除语义，以支持历史数据回填。
4. 将所有 `iteration_id` 为空的需求迁入其所属项目需求池，包括需要满足非空约束的历史软删除数据。
5. 审计项目引用、需求池标识、单项目关联、需求空归属和悬空引用。
6. 审计通过后将 `requirements.iteration_id` 收紧为非空并增加外键。

迁移必须可在隔离数据库中验证，但不依赖重复执行来承担运行时修复职责。

## 9. 测试范围

- 创建项目自动生成并引用唯一需求池，失败时事务回滚。
- 普通迭代的 `is_requirement_pool` 始终为 `0`，客户端不能伪造需求池。
- 创建需求默认进入需求池，明确选择正式迭代时保持选择结果。
- 清空需求迭代、从正式迭代移除需求时进入需求池且历史完整。
- 需求换项目时按当前归属执行自动换池或正式迭代范围校验。
- 导入新增需求默认进入需求池，更新逻辑不误覆盖现有正式迭代。
- 需求池允许有权限用户重命名，但禁止修改其他字段、删除和流转。
- 需求池不进入正常迭代列表、详情入口、工作台、燃尽图和交付统计。
- 项目需求池关系损坏时返回数据完整性错误，不创建第二个需求池。
- 迁移后不存在空 `requirements.iteration_id`、悬空引用、错误标识或错误项目关联。
- 回归普通迭代创建、编辑、删除、流转、延期和多项目关联能力。

## 10. 验收标准

- 任意新建或存量需求都有有效的 `iteration_id`。
- 每个项目都能通过 `requirement_pool_iteration_id` 唯一定位其需求池。
- 用户未排期需求时不会被阻塞，需求自动归入项目需求池。
- 需求池名称可修改，但其系统身份和保护规则不会随名称变化。
- 需求池不会污染正式迭代工作台和交付统计。
- 所有需求迭代归属变化均可通过历史记录追溯。
