# 后续问题清单

## 使用范围

## 问题状态

- 待确认：已收到现象，尚未稳定复现或确认影响。
- 待计划：已确认问题，等待制定执行计划。
- 待实施：计划已确认，等待集中处理。
- 实施中：正在修复或补充自动化测试。
- 待验证：实现已完成，等待回归与验收。
- 已解决：验证通过，保留问题、计划和验证证据。

## 已解决

### N-001 项目配置页允许解绑工作流方案

- 状态：已解决
- 类型：功能缺陷
- 优先级：P1
- 发现时间：2026-08-04
- 影响范围：项目详情页的“配置”页签。
- 复现步骤与证据：进入任一项目详情的“配置”页签；“工作流方案”选择框右侧展示清除图标，点击后可清空当前方案绑定。
- 预期结果：项目始终保留一个工作流方案；用户只能从下拉选项中切换方案，不能清空绑定。
- 实际结果：`frontend/src/views/ProjectDetailView.vue` 的工作流方案选择器声明了 `clearable`，前端允许将绑定值设为 `null`。
- 根因分析：项目详情配置页未与项目列表创建/编辑页保持“禁止清除工作流方案”的控件约束一致。
- 执行计划：
  1. 为项目详情工作流方案选择器补充前端源契约测试，断言该选择器不含 `clearable`。
  2. 移除 `ProjectDetailView.vue` 该选择器的 `clearable` 属性，保留切换、重置和保存逻辑。
  3. 执行前端测试与构建，并在项目配置页验证只能切换、不能解绑。
- 验证结果：已于 2026-08-04 合并至本地 `main`（提交 `6f32741`，合并提交 `acdb3b6`）；定向契约测试 `npm test projectDetailWorkflowIterationLayout` 与 `npm run build` 均通过，预览服务返回 HTTP 200。

### N-002 项目详情迭代页将需求池与交付迭代拆为两张表

- 状态：已解决
- 类型：体验问题
- 优先级：P2
- 发现时间：2026-08-04
- 影响范围：项目详情页的“迭代”页签。
- 复现步骤与证据：进入仅包含默认需求池、尚未创建普通迭代的项目详情；页面先展示需求池表头和一条“需求池（未排期）”记录，再展示一张空的交付迭代表格及相同表头。
- 预期结果：需求池与普通迭代显示在同一张迭代表格中；需求池保持现有“需求池（未排期）”标识，无需重复表头。
- 实际结果：`ProjectDetailView.vue` 先单独渲染 `projectRequirementPoolRow`，又渲染经 `deliveryIterations()` 过滤后的 `pagedProjectIterations`，造成两张同列结构的表格。
- 根因分析：需求池为保证默认显示而被从交付迭代数据中分离，但视图层未复用同一份行数据和列定义。
- 执行计划：
  1. 为项目详情迭代页补充前端源契约测试，断言需求池和交付迭代共用一个 `el-table`，且需求池行仍采用 `requirementIterationLabel()` 显示标识。
  2. 在 `ProjectDetailView.vue` 构造“需求池优先、普通迭代随后”的统一行数据，删除单独的需求池表格。
  3. 保留需求池不可删除、不可流转及可编辑的既有操作限制；分页、搜索和普通迭代操作仅作用于对应数据范围。
  4. 执行前端测试与构建，并验证仅有需求池、需求池加普通迭代、无搜索结果三种场景均只显示一行表头。
- 验证结果：已于 2026-08-04 合并至本地 `main`（提交 `6f32741`，合并提交 `acdb3b6`）；定向契约测试 `npm test projectDetailWorkflowIterationLayout` 与 `npm run build` 均通过，预览服务返回 HTTP 200。

### N-003 缺少迭代负责人专属权限边界

- 状态：已解决
- 类型：权限与流程改造
- 优先级：P2
- 发现时间：2026-08-04
- 影响范围：迭代详情、项目详情迭代页、迭代工作项范围管理和迭代审计。
- 现状与问题：迭代存在负责人字段，但未形成明确的专属权限模型，容易与项目负责人、工作项当前处理人混淆。
- 确认规则：迭代负责人只负责交付节奏和范围管理，可查看迭代范围与阻断项、编辑名称/目标/计划日期、执行迭代生命周期动作、纳入/移出/延期工作项并查看完成快照；不得修改项目配置、成员、工作流方案或业务组件，也不得仅凭迭代负责人身份编辑工作项内容、变更工作项处理人或执行工作项流转。
- 约束：迭代负责人必须是项目有效成员；成员失效后禁止继续操作并要求重新指定。项目负责人、上级项目负责人和系统管理员可覆盖操作，但必须写入审计原因。项目关闭后冻结该权限。迭代负责人变更和迭代删除仅由项目负责人或系统管理员执行。
- 执行计划：
  1. 梳理迭代生命周期、范围管理、详情查看、负责人变更和删除各入口，建立允许/拒绝的 API 测试矩阵。
  2. 在后端权限服务中新增独立的迭代负责人判定与操作级校验，避免复用项目治理或工作项权限。
  3. 调整前端按钮可见性和禁用状态，使迭代负责人仅看到职责范围内的操作。
  4. 补齐审计字段与成员失效、项目关闭、覆盖操作的回归测试。
- 验证结果：后端定向权限矩阵 `pytest tests/test_iteration_owner_permission_api.py tests/test_project_permission_boundary_api.py -q` 通过（16 passed）；前端 `npm test` 与 `npm run build` 通过。

### N-004 迭代完成或取消的阻断弹窗出现横线

- 状态：已解决
- 类型：体验问题
- 优先级：P2
- 发现时间：2026-08-04
- 影响范围：项目详情与迭代详情中，触发“完成”或“取消”后因未完成事项被阻断的弹窗。
- 复现步骤与证据：对存在未完成事项的迭代点击“完成”或“取消”；出现“存在未完成事项，无法结束迭代”弹窗时，遮罩层中横跨页面显示一条直线。
- 预期结果：阻断弹窗及遮罩层正常覆盖页面，不出现来自底层表格的横线或布局残留。
- 实际结果：`WorkflowActionButtons.vue` 的通用工作流表单弹窗带有 `append-to-body`，但阻断弹窗未设置该属性；阻断弹窗由迭代表格行内的动作组件创建，容易与表格容器叠加。
- 根因分析：阻断弹窗未挂载到 `body`，其遮罩与对话框仍受列表行所在 DOM 层级影响。
- 执行计划：
  1. 为阻断弹窗补充前端源契约测试，断言其与通用工作流弹窗一致声明 `append-to-body`。
  2. 在 `WorkflowActionButtons.vue` 的 `blockerDialogVisible` 对话框上增加 `append-to-body`，不改变阻断数据、筛选和关闭行为。
  3. 执行前端测试与构建，并在项目详情和迭代详情分别触发完成/取消阻断，确认横线消失。
- 验证结果：`node src/components/workflowActionButtonsBehavior.test.mjs`、前端 `npm test` 与 `npm run build` 通过；阻断弹窗已声明 `append-to-body`。

### N-005 项目详情迭代操作栏按钮间距和对齐不一致

- 状态：已解决
- 类型：体验问题
- 优先级：P2
- 发现时间：2026-08-04
- 影响范围：项目详情页“迭代”页签的操作列。
- 复现步骤与证据：在存在可执行流转动作的普通迭代行中，观察“更多”“延期工作项”“编辑”“删除”；按钮间距不均，文字基线和可点击区域未形成统一操作栏。
- 预期结果：迭代行的所有操作以同一 flex 容器排列，统一垂直居中、间距和最小点击区域；需求池仍只显示允许的“编辑”操作。
- 实际结果：`ProjectDetailView.vue` 将 `WorkflowActionButtons`、延期、编辑和删除按钮直接放在同一模板中。工作流按钮组件内部使用独立 flex 间距，后续 Element Plus 按钮使用默认外边距，导致视觉不齐。
- 根因分析：迭代操作列没有复用已有的 `.table-actions` 统一布局类，多个操作来源的按钮缺少共同容器。
- 执行计划：
  1. 补充前端源契约测试，断言迭代操作列使用 `.table-actions` 容器。
  2. 用该容器包裹工作流动作、延期、编辑和删除操作；保留现有权限和需求池条件，不调整动作顺序。
  3. 执行前端测试与构建，并验证普通迭代与需求池行的操作栏均水平对齐、间距一致。
- 验证结果：`node src/views/projectDetailWorkflowIterationLayout.test.mjs`、前端 `npm test` 与 `npm run build` 通过；迭代操作列已使用 `.table-actions`。

### N-006 项目详情需求操作栏固定展示“编辑”，与工作流配置重复

- 状态：已解决
- 类型：功能与体验问题
- 优先级：P1
- 发现时间：2026-08-04
- 影响范围：项目详情页“需求”页签的操作列。
- 复现步骤与证据：在工作流方案高级配置中将需求“编辑”动作设置为“更多”后，项目详情需求行仍固定显示“编辑”，同时“更多”菜单也包含“编辑”。
- 预期结果：需求的“编辑”仅按工作流方案高级配置显示；生成任务、建用例和删除继续作为页面固有操作保留。
- 实际结果：`ProjectDetailView.vue` 在 `WorkflowActionButtons` 前固定渲染 `openRequirementEdit(row)` 的“编辑”按钮；工作流动作组件又按当前状态和高级配置渲染“编辑”。
- 根因分析：固定页面操作与工作流动作没有划分职责，导致同一编辑命令存在两条入口。
- 执行计划：
  1. 补充前端源契约测试，断言项目详情需求操作列不再固定渲染 `openRequirementEdit(row)`，但仍保留工作流动作组件、生成任务、建用例和删除。
  2. 移除需求操作列的固定“编辑”按钮；不改动 `WorkflowActionButtons` 的高级配置解析和 `openRequirementEdit` 命令处理。
  3. 执行前端测试与构建，并分别验证“编辑”配置为主操作、更多操作、隐藏时的展示符合方案配置。
- 验证结果：`node src/views/projectDetailWorkflowIterationLayout.test.mjs`、前端 `npm test` 与 `npm run build` 通过；需求固定编辑入口已移除，仅保留工作流动作入口。
