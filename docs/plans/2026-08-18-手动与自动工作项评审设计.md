# 手动与自动工作项评审设计

## 目标

需求、任务和 Bug 均支持手动提交评审与 DevOps 提交自动触发评审。两种入口共用同一评审记录、权限、Diff 上下文和评审决定流程。

## 适用范围

- 工作项类型：需求、任务、Bug。
- 状态流转：处理中或修复中提交评审，待评审通过后进入后续验证状态；评审不通过后回到处理中或修复中。
- 页面：工作台、项目详情列表与详情页中的流转操作，以及待评审弹窗。

## 交互与流程

1. 当前处理人可手动点击“提交评审”。系统创建或复用开放中的评审记录，并将工作项流转到待评审。
2. DevOps 接收到关联工作项的提交时，系统自动提交评审；若已有开放评审记录，则更新其最新提交与 Diff，不重复创建评审轮次。
3. 在待评审状态，流程配置中获授权的评审角色看到单一“评审”按钮。点击后打开评审弹窗。
4. 弹窗优先展示评审记录关联提交的 Git Diff；不存在关联提交，或提交没有 Diff 内容时，显示“未找到 Git Diff 片段”。
5. “评审通过”执行既有通过流转，进入对应的待验证状态；“评审不通过”必须填写理由，执行既有驳回流转并回到处理中或修复中。
6. 手动提交、自动提交、通过和驳回均记录操作人、时间、入口、关联提交和驳回理由。

## 后端设计

- 扩展统一评审服务，支持无关联提交的手动评审记录，以及带关联提交的自动评审记录。
- 提供评审上下文查询接口，返回工作项、开放评审记录和可展示的 Diff；没有 Diff 时显式返回可识别的空上下文。
- 评审决定接口继续作为通过与驳回的唯一入口，服务端校验评审角色与驳回理由。
- 手动和自动提交均通过统一服务执行 `submit_review`，以保证状态迁移与评审记录原子一致；自动入口仅补充提交链接，不替代手动入口。

## 前端设计

- 增加可复用的工作项评审弹窗，在工作台、项目详情列表和详情页中复用。
- 隐藏待评审状态下分散的“评审通过”“评审驳回”直接操作，统一展示“评审”按钮。
- 弹窗复用现有 Diff 查看器；空内容使用“未找到 Git Diff 片段”提示，不阻止评审决定。
- 驳回按钮先要求填写不通过理由，再调用评审决定接口。

## 工作流模板升级

- 默认需求、任务和 Bug 模板中的“提交评审”改为可人工执行的流转，不再仅标记为系统动作。
- 自动提交仍保留，由 DevOps 关联提交调用同一评审提交服务触发。
- 待评审状态的通过、驳回流转配置为评审弹窗的内部决定动作，避免以两个独立按钮暴露。
- 为已存在的默认工作流提供幂等升级，保留用户自定义工作流和既有历史记录。

## 异常与验收

- 没有 Git 提交或 Diff 时，评审弹窗必须显示“未找到 Git Diff 片段”。
- 没有开放评审记录时，不允许直接作出评审决定。
- 无权用户不可提交评审、打开评审决定或作出通过、驳回。
- 自动提交与手动提交并发时，最多保留一条开放评审记录。
