# 项目待规划工作池设计

## 问题与目标

每个项目已有一个系统默认的需求池迭代，用于保证需求总有迭代归属。但它在项目迭代列表中表现得像普通迭代，无法回答项目还有多少需求、任务、Bug 尚未纳入具体执行迭代。

将该默认迭代定义为“待规划工作池（未排期）”。它是项目的唯一未排期工作容器，不是交付迭代，作用是提供统一、可信、可操作的计划存量视图。

## 范围

包含项目概览、项目迭代页、项目内需求/任务/Bug 列表、三类事项的创建和流转约束，以及历史数据回填。

不修改工作台，工作台既有的待处理、未分派、已完成、已终止视图和统计口径保持不变。

## 工作池规则

1. 每个项目保留一个由 `is_requirement_pool` 和 `requirement_pool_iteration_id` 标识的系统工作池；不增加新模型。
2. 未显式选择正式执行迭代的新需求、独立任务、独立 Bug 自动绑定工作池。
3. 从需求生成的任务继承需求迭代；关联 Bug 在来源事项已处于正式迭代时继承该迭代，否则进入工作池。
4. 工作项从工作池移动到计划中或进行中的正式迭代后，不再计入待规划数量。需求移动时继续同步其关联任务；Bug 不因需求移动被强制迁移，以保留缺陷独立排期能力。
5. 工作池中的事项不能开始处理、完成或终止。需要执行时，用户必须先选择正式执行迭代；系统在同一事务中完成迭代迁移与工作流流转。
6. 统计只计算 `iteration_id` 为当前项目工作池、且状态非终态的需求、任务、Bug。该约束成立后，工作池中的总量即为待规划量，无需展示“已完成 / 总数”。

## 项目内体验

### 项目概览

在概览顶部的项目内容区域展示一条全宽“待规划工作池”信息带，主指标为“待规划 N 项”，并显示需求、任务、Bug 分项。数量为零时保持低干扰的完成态；大于零时使用醒目的警示层级，不使用与执行迭代相同的状态样式。

信息带提供两个动作：

- 查看事项：进入项目内工作项视图，并预置工作池迭代筛选；
- 纳入迭代：选择一个计划中或进行中的正式迭代，批量移动选中事项。

### 项目迭代页

工作池从普通数据行提升为迭代列表顶部的信息带。它不展示负责人、开始结束日期或迭代流程操作；仅展示待规划总量、三类分项、查看事项和纳入迭代。正式迭代继续在下方表格显示。

### 项目工作项页

需求、任务、Bug 列表增加“迭代”筛选中的“待规划工作池”快捷选项。选择后只显示本项目对应工作池内的该类事项，便于核对并批量纳入执行迭代。

## 权限和历史数据

项目成员可以查看工作池和数量。项目负责人、项目管理员或已有迭代管理权限的成员可纳入迭代；创建事项仍沿用现有创建权限。

数据迁移时，将任务和 Bug 的空 `iteration_id` 回填至其项目工作池。历史上处于工作池的终态事项不计入统计，迁移输出清单供管理员归档到对应历史迭代；新规则生效后不允许再产生此类数据。

## 验证

后端覆盖创建默认归属、来源继承、工作池流转拦截、统计和历史回填；前端覆盖工作池信息带、项目内筛选和权限展示。执行相关 pytest、前端测试和生产构建。工作台测试用于证明其未被修改或回归。
