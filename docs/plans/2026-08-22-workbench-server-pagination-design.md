# 工作台服务端分页性能优化设计

## 根因

工作台页面当前只展示一张“进行中迭代工作项”表，但后端 `get_workbench()` 仍组装全部历史工作台分区。每个分区分别查询需求、任务和 Bug，多处使用 `.all()` 后再以 Python 过滤；旧任务的有效迭代还可能逐条查询。前端在完整 `active_iteration_items` 上执行筛选、排序和分页，然后为完整集合请求工作流动作。上百条数据会同时放大数据库查询、Python 对象构造、JSON 响应、前端计算和动作解析成本。

## 方案比较

1. 前端虚拟滚动：只降低 DOM 节点数量，无法减少接口和动作请求，不能解决根因。
2. 缓存完整聚合响应：读取变快，但权限、状态、关注和工作流动作的失效复杂，且首次计算仍慢。
3. 专用服务端分页接口：数据库完成筛选、计数、排序和分页，页面只加载当前页；旧接口保留兼容。该方案数据量增长时成本可控，采用此方案。

## 接口

新增 `GET /api/v1/dashboard/workbench/items`：

- 参数：`page`、`page_size`、`keyword`、`project_ids`、`iteration_ids`、`object_types`、`state_ids`、`priorities`、`handler_ids`。
- `page >= 1`，`1 <= page_size <= 100`。
- 响应：`items`、`total`、`page`、`page_size`、`page_count`、`filter_options`。
- 权限范围复用现有工作台项目范围和系统管理员全局范围。
- 工作项范围保持为进行中迭代中的需求、任务和 Bug，包括终态工作项。
- 旧 `/dashboard/workbench` 不修改响应协议。

## 查询

将三类工作项投影为统一查询列，使用 `UNION ALL` 形成只读子查询。任务迭代使用 `COALESCE(task.iteration_id, requirement.iteration_id)` 兼容历史关联任务。外层查询统一关联项目、迭代和当前工作流状态，在 SQL 中应用权限及筛选条件。

总数使用同一过滤子查询 `COUNT(*)`，数据查询使用稳定顺序和 `LIMIT/OFFSET`。排序延续当前页面语义：非终态优先、逾期优先、优先级升序、截止日期升序、更新时间降序，最后以对象类型和 ID 保证稳定翻页。

筛选选项从用户完整可见的进行中迭代范围执行 `DISTINCT` 查询，不从当前页推导，防止翻页后选项消失。

## 前端

- 页面直接消费服务端 `items/total/filter_options`，移除全量客户端过滤、排序和切片。
- 页码、页大小改变时重新请求；筛选改变时回到第一页并防抖请求。
- 加载工作流动作时只传当前页 `items`，最大数量受 `page_size` 限制。
- 刷新、批量指派、编辑和工作流执行完成后重新加载当前查询条件；若当前页因删除变空则回退到最后有效页。
- 保持现有表格、筛选控件和批量操作体验，不引入虚拟滚动。

## 性能门槛

- 120 条可见工作项、页大小 20 时，分页接口只返回 20 条且 `total=120`。
- 工作流动作批量请求最多包含当前页条数。
- 分页接口 SQL 查询数量不随工作项条数线性增长，不出现逐任务有效迭代查询。
- 过滤、翻页不调用旧聚合接口。

## 验证

后端覆盖分页边界、全部筛选、权限隔离、历史任务有效迭代和稳定排序；前端契约覆盖服务端参数、筛选防抖、总数和当前页动作加载。最后运行工作台后端回归、前端全量测试和生产构建。
